CI/CD LABS LAB 01: FIRST PIPELINE

01 / First Pipeline

Ship a green CI pipeline on GitHub Actions. The objective is to close the loop: trigger a pipeline via a push, execute a build and test sequence on a hosted runner, and surface the status as a check on the Pull Request.

01 PUSH Webhook trigger PASSED
02 CHECKOUT actions/checkout PASSED
03 SETUP Node 20 + cache PASSED
04 CI npm ci PASSED
05 TEST npm test RUNNING

OBJECTIVE

Establish the smallest closed loop in CI/CD: a developer pushes code, an automated system validates it, and the result is fed back to the source control platform.

ARCHITECTURE

Push → GitHub webhook → hosted runner (ubuntu-latest) → checkout → setup-node → npm ci → npm test → green check on PR.

Step 1: Add the Workflow

Create .github/workflows/ci.yml in the repository. This declarative YAML defines the trigger, the execution environment, and the sequence of steps.

name: ci on: [push, pull_request] jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 20, cache: npm } - run: npm ci - run: npm test

EXPECTED RESULT

Push to a branch and open a PR. The Actions tab shows the run executing. The PR view displays a green checkmark indicating the status check passed.

CI/CD LABS BRANCH PROTECTION

02 / Enforce the Gate

An unenforced gate is decoration. A green check on a PR is meaningless if a developer can click "Merge" while the pipeline is red. Branch protection converts the CI result from a suggestion into a rule.

Step 2: Require the Check

Navigate to Repo Settings → Branches → protect main. Require the build status check to pass before merging.

IS CI STATUS GREEN?
YES
MERGE ALLOWED main branch updated
NO
MERGE BLOCKED Button disabled

Verification & Failure Scenarios

  • PR shows green check from the workflow.
  • Merging to main without green is blocked.
  • Breaking the test turns the PR red.

GOTCHA

If npm ci fails, it usually means the lockfile is missing or out of sync. Run npm install locally, commit the package-lock.json file, and push again. Do not use npm install in CI; npm ci enforces hermetic, reproducible builds.

INTERVIEW CHECK

Q: What does the green check actually prove?

A: It proves that the specific code at that specific commit passed the specific checks defined in the YAML. It does not prove the application is bug-free. Breaking the test on purpose is the real verification—it proves the pipeline catches failures.

CI/CD LABS LAB 02: BUILD AND TEST

03 / Build and Test DAG

Split Lab 01's single job into a fast, cached PR pipeline. By separating the build and test phases into distinct jobs, we create a Directed Acyclic Graph (DAG) that optimizes execution and isolates failures.

01 BUILD npm ci PASSED
02 TEST needs: build RUNNING
03 CHECK Combined status WAITING

OBJECTIVE

Create a hermetic build job followed by a unit test job. Total execution time should be under 10 minutes, with reruns benefiting from warm npm caches.

THE DAG EDGE

The needs: keyword in GitHub Actions defines the DAG edge. The test job will not execute until the build job completes successfully.

Step 1: Split and Cache

jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 20, cache: npm } - run: npm ci test: needs: build runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 20, cache: npm } - run: npm ci - run: npm test
CI/CD ENGINEERING MANUAL LAB 02  |  04 / 07
CI/CD LABS HERMETIC BUILDS

04 / Hermeticity & Caching

A build is hermetic if it produces the exact same result regardless of the environment it runs in. In CI, this means the runner should not rely on ambient machine state. The lockfile is the contract.

Step 2: Prove Hermeticity

EXECUTE

Delete node_modules locally. Run npm ci && npm test. The result should be identical to the CI runner.

VERIFY

Two jobs visible in GitHub Actions, ordered by needs. Cache hit shown on rerun. Local npm ci reproduces CI result.

GOTCHA

If the cache never hits, the lockfile is likely not committed, or the key inputs have changed. The actions/setup-node action uses the lockfile to key the cache. If package-lock.json is in .gitignore, caching fails silently.

LOCAL COMMAND

$ rm -rf node_modules $ npm ci

EXPECTED RESULT

added 42 packages, audited 43 packages Identical to runner install

INTERVIEW CHECK

Q: What does needs: actually guarantee?

A: It guarantees that the downstream job will not start until the upstream job completes successfully. If the build job fails, the test job is skipped, saving compute time and preventing tests from running against a broken build.

CI/CD ENGINEERING MANUAL SUMMARY  |  06 / 07
CI/CD LABS LAB 03: ARTIFACTS

01 / Artifact Immutability

Build a Docker image once, tag it by commit SHA, push it to GitHub Container Registry (GHCR), and attach a Software Bill of Materials (SBOM). The objective is to establish a single, immutable deployable identity that flows through all environments.

01 MERGE main branch PASSED
02 BUILD Multi-stage PASSED
03 TAG sha-<short> RUNNING
04 PUSH Github GHCR WAITING
05 SBOM Generate list WAITING

OBJECTIVE

Create an immutable artifact tagged by commit SHA, push it to a registry, and attach an SBOM. Prove that staging and production would run the exact same digest.

IMMUTABILITY

A tag like :latest is mutable; it can point to different bytes over time. A SHA tag (sha-a1b2c3d) and the underlying digest are permanent. The digest is the true deployable identity.

Step 1: Build Once, Tag SHA

The workflow uses GitHub Actions to build the image, log into GHCR using the built-in GITHUB_TOKEN, tag the image with the commit SHA, and push it.

jobs: image: runs-on: ubuntu-latest permissions: { packages: write } steps: - uses: actions/checkout@v4 - uses: docker/login-action@v3 with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} } - uses: docker/metadata-action@v5 id: meta with: images: ghcr.io/${{ github.repository }} tags: type=sha,prefix=sha- - uses: docker/build-push-action@v6 with: { push: true, tags: ${{ steps.meta.outputs.tags }} }

EXPECTED RESULT

GHCR shows the sha-<short> tag. The GitHub Actions logs print the immutable image digest, which will be used for deployment.

CI/CD ENGINEERING MANUAL LAB 03  |  02 / 07
CI/CD LABS SBOM & VERIFICATION

02 / Software Bill of Materials

An artifact is a black box. An SBOM (Software Bill of Materials) is the ingredient list. It makes the next CVE answerable in minutes, not days, by explicitly listing every package and dependency baked into the image.

Step 2: Attach SBOM

Add the anchore/sbom-action to the workflow immediately after the image is pushed. This action scans the image and attaches the resulting SBOM as a workflow artifact.

COMMAND

- uses: anchore/sbom-action@v0 with: image: ghcr.io/${{ github.repository }}:sha-${{ github.sha }} format: spdx-json

RESULT

[Pipeline] stage SBOM generated successfully. Artifact: sbom-spdx.json Packages scanned: 142

Verification & Failure Scenarios

  • GHCR holds an immutable SHA tag.
  • Same digest referenced twice equals same bytes.
  • SBOM artifact present in the workflow run.

GOTCHA

If the push fails with a 403 Forbidden error, the workflow is missing the packages: write permission. GitHub Actions tokens are least-privilege by default; you must explicitly grant write access to packages.

INTERVIEW CHECK

Q: Digest vs tag: why is redeploying :latest dangerous?

A: A tag is a pointer. If you deploy :latest, you are deploying whatever bytes the registry currently points to. If someone pushes a new image to :latest, your deployment silently changes. Pinning the digest (sha256:...) guarantees the exact bytes.

CI/CD LABS LAB 04: DEPLOYMENT

03 / Environment Promotion

Continuous Delivery means the software is always releasable, but release is a human decision. Promote Lab 03's immutable digest through staging to production with an explicit approval gate. Same digest, two environments.

STAGING
Auto-deploy on merge ACTIVE
PRODUCTION
Manual approval required GATED

Step 1: Staging Auto-Deploys

The staging deployment is fully automated. It depends on the image job from Lab 03 and deploys the specific digest output by that job.

deploy-staging: needs: image environment: staging runs-on: ubuntu-latest steps: - run: echo "deploy ${{ needs.image.outputs.digest }} to staging"

WHY IT MATTERS

Staging proves the artifact continuously. Automation here is safe because users never see it. If the artifact fails in staging, the pipeline halts before reaching the production gate.

CI/CD ENGINEERING MANUAL LAB 04  |  04 / 07
CI/CD LABS THE PRODUCTION GATE

04 / The Production Gate

Production deployment requires a human decision. By utilizing GitHub Environments and required reviewers, the pipeline pauses automatically, waiting for approval before applying the same digest to production.

APPROVE PRODUCTION DEPLOYMENT?
APPROVE
EXECUTE PROD DEPLOY terraform apply / kubectl apply
REJECT
HALT PIPELINE Staging remains active

Step 2: Production Needs a Human

deploy-prod: needs: [deploy-staging] environment: production runs-on: ubuntu-latest steps: - run: echo "deploy ${{ needs.image.outputs.digest }} to prod"
  • Staging deploys on every merge, no clicks.
  • Production blocks until approved by a reviewer.
  • Both environments ran the identical image digest.

GOTCHA

If digests differ between environments, the pipeline passed a tag (like :latest or main) instead of the explicit digest. Always pass ${{ needs.image.outputs.digest }} explicitly to guarantee byte-for-byte parity.

CI/CD LABS LAB 05: ROLLBACK

01 / The Incident & Recovery

Break production deliberately, then recover by redeploying the previous known-good digest. The objective is to prove that recovery is a practiced path, not an improvised fire drill. Green pipelines do not guarantee correct applications; tests only cover what you thought of.

01 MERGE Bad code change PASSED
02 STAGING Tests miss bug PASSED
03 PROD Visible breakage FAILED
04 ROLLBACK Redeploy previous WAITING
05 POSTMORTEM Fix pipeline PENDING

OBJECTIVE

Cause an incident, recover by rolling back to a previously deployed artifact digest, and write a postmortem that results in a merged pipeline change.

WHY RECOVERY?

Recovery must be engineered. If your only recovery mechanism is "git revert and rebuild," you are adding untested variables to a fire. Old digests are proven; fresh builds are risks.

Step 1: Cause the Incident

Merge a change that passes all CI tests but breaks the application's visible output (e.g., changing a port or breaking a route). Promote this change to production.

EXPECTED RESULT

Production is broken despite a green pipeline. This proves the gap between "tests pass" and "application works."

CI/CD ENGINEERING MANUAL LAB 05  |  02 / 07
CI/CD LABS ROLLBACK & POSTMORTEM

02 / Rollback & Postmortem

When production is broken, the fastest path to recovery is redeploying the last known-good state. Do not rebuild; redeploy the exact immutable digest that ran before the incident.

HAS DATA BEEN MIGRATED FORWARD?
YES
FORWARD-FIX Expand/Contract pattern
NO
ROLLBACK Redeploy old digest

Step 2: Roll Back, Don't Rebuild

EXECUTE

Redeploy the previous known-good digest to production. Re-run the old deploy-prod job or dispatch a new run with the saved digest value. Time yourself.

VERIFY

Production is healthy again within minutes. No fresh build was involved.

Step 3: Postmortem with Teeth

Timeline: 10:00 Bad merge deployed 10:05 Users report 500 errors 10:07 Team declares incident 10:09 Rollback initiated (digest: sha-a1b2c3d) 10:12 Production healthy Action Item: Add integration test for port binding

GOTCHA

If the previous digest is unknown, rollback is impossible. You must log every deployed digest in an immutable audit log. Without the digest, you are forced to rebuild, introducing untested variables into an active incident.

INTERVIEW CHECK

Q: Rollback vs forward-fix: which failure forces expand-contract instead of reverting?

A: If a database migration has already executed and modified data schemas (forward-only migration), a code rollback will fail because the old code cannot read the new schema. You must forward-fix using an expand-contract pattern.

With the agent connected, create a new Pipeline job. The pipeline must explicitly target the docker-agent label to prove scheduling works. The script contains the minimal three stages required to demonstrate execution and visualization.

pipeline { agent { label 'docker-agent' } stages { stage('Build') { steps { sh 'echo build' } } stage('Test') { steps { sh 'echo test' } } stage('Deploy'){ steps { echo 'deploy' } } } }

Q: down vs down -v: which one wipes jenkins_home?

CI/CD LABS LAB 07: SHARED LIBRARY

01 / Pipeline Code Reuse

As pipeline complexity grows, duplicating Groovy logic across dozens of Jenkinsfiles creates a maintenance nightmare. Extract a duplicated pipeline step into a versioned shared library consumed by multiple pipelines, achieving reuse without copy-paste.

01 EXTRACT Isolate logic PASSED
02 VERSION Git repository PASSED
03 REGISTER Jenkins global config RUNNING
04 CONSUME @Library annotation WAITING
05 VERIFY DRY payoff WAITING

OBJECTIVE

Move a shared step into a standalone Git repository, configure Jenkins to use it as a Global Pipeline Library, and call it from two distinct pipelines.

ARCHITECTURE

Library repo (vars/standardTest.groovy) → Jenkins Global Pipeline Libraries → multiple Jenkinsfiles call the same step → one fix propagates to all consumers.

Setup: The Library Repository

Create a repository named pipeline-library. Inside, create a directory named vars and a file standardTest.groovy. This file defines a custom step that can be called by any pipeline.

# File: vars/standardTest.groovy def call(Map cfg = [:]) { sh "\${cfg.cmd ?: 'npm test'}" }

WHY IT MATTERS

Versioned libraries are dependencies. They are pinned, reviewed, and rollback-able. Copy-pasted steps are untrackable; shared libraries bring standard software engineering practices to pipeline code.

CI/CD ENGINEERING MANUAL LAB 07  |  02 / 07
CI/CD LABS LIBRARY CONSUMPTION

02 / Registration & Consumption

With the library code in a Git repository, Jenkins must be configured to trust and load it. Once registered, pipelines can import the library using an annotation.

Step 1: Register the Library

Manage Jenkins -> System -> Global Pipeline Libraries > Library Name: my-lib > Default Version: main > Retrieval Method: Modern SCM > Project Repository: https://github.com/user/pipeline-library.git

Step 2: Consume from Two Pipelines

In both Jenkinsfiles, import the library and call the custom step. The _ in the annotation tells Jenkins to import the library but not run any global scripts automatically.

@Library('my-lib') _ pipeline { agent { label 'docker-agent' } stages { stage('Test') { steps { standardTest(cmd: 'npm test') } } } }
  • Both pipelines call the library step successfully.
  • Breaking the library breaks both (proves sharing); reverting fixes both.
  • Library change went through PR review on its own repo.

GOTCHA

If you encounter Library my-lib not found, check two things: the name in the Jenkinsfile matches the Global config exactly, and the default version (e.g., main) exists in the repository.

CI/CD ENGINEERING MANUAL LAB 08  |  05 / 07
CI/CD LABS BACKUP & RESTORE

05 / The Procedure

Execute the disaster recovery drill. The process involves stopping the container, archiving the volume, wiping the slate clean, and rebuilding from the archive.

Step 1: Back Up

$ docker compose stop jenkins $ docker run --rm -v jenkins-lab_jenkins_home:/data \ -v "$PWD":/out alpine tar czf /out/jenkins-backup.tar.gz -C /data . jenkins-backup.tar.gz created successfully. $ docker compose start jenkins

Step 2: Destroy and Restore

$ docker compose down -v # Wipe EVERYTHING $ docker compose up -d # Fresh controller $ docker compose stop jenkins $ docker run --rm -v jenkins-lab_jenkins_home:/data \ -v "$PWD":/in alpine tar xzf /in/jenkins-backup.tar.gz -C /data $ docker compose start jenkins Restore complete. Jenkins initializing...

Verification Checklist

  • Job list + history identical (check the recorded build number).
  • Credential ID present and usable.
  • Smoke pipeline (from Lab 06) runs green on the restored controller.

GOTCHA

If you restore on a different Jenkins image tag, you may encounter plugin version drift. Always pin the jenkins:lts image digest for both controller and backup to guarantee compatibility. If permission errors occur, ensure the volume is owned by UID 1000 (chown -R 1000:1000).

CI/CD ENGINEERING MANUAL SUMMARY  |  07 / 07
CI/CD SYSTEMS AUTOMATED TRIGGERING

01 / Automated Integration Foundations

A pipeline is not magic. It is a deterministic sequence of machines making decisions about your code. However, for this sequence to be truly continuous, the transition between a developer's commit and the pipeline execution must be automatic. This is achieved through webhooks.

01 COMMIT git push origin main PASSED
02 WEBHOOK HTTP POST payload RUNNING
03 JENKINS Trigger detected WAITING
04 CHECKOUT Pull repository WAITING
05 BUILD Execute pipeline WAITING

WHAT

A webhook is a custom HTTP callback triggered by an event, such as a git push. When the event occurs, the source system (GitHub) sends an HTTP POST request to the target system (Jenkins).

WHY

Polling (Jenkins constantly asking GitHub "any changes?") is inefficient and introduces latency. Webhooks provide instant, event-driven execution with zero wasted resources.

WHEN

Whenever a change is pushed to the repository. This includes commits to main, feature branches, or tagged releases, depending on the configured filter.

WHAT CHANGES

The development loop tightens. Feedback on a broken commit returns in minutes, not hours. The integration of code becomes a continuous, automatic flow rather than a manual chore.

WHY THIS EXISTS

Without automated triggering, a developer must manually notify the CI system that new code exists. This context switch breaks flow and inevitably leads to forgotten builds and integration delays. The webhook closes the gap between intent and execution.

03 / Reachability & Network Paths

The webhook requires a clear HTTP path from GitHub's servers to your Jenkins instance. This is the most common point of failure in CI/CD automation. Determine your network topology before setting the Payload URL.

IS JENKINS PUBLICLY REACHABLE?
YES
USE DIRECT URL https://jenkins.company.com
NO
USE TUNNEL ngrok http 8080

Establishing the Tunnel

If Jenkins is behind a NAT or local firewall, route traffic through a tunnel. This provides a temporary public URL that forwards incoming HTTP requests directly to your local port.

COMMAND

$ ngrok http 8080

RESULT

Forwarding https://1a2b-3c4d.ngrok.io -> http://localhost:8080

INTERVIEW CHECK

Q: Why can't I just use my local IP for the webhook?

A: GitHub's webhooks are sent from their public cloud infrastructure. Your local machine's IP (e.g., 192.168.x.x) is not routable from the public internet. A tunnel or public IP is required to bridge the connection.

CI/CD ENGINEERING MANUAL CH 01  |  04 / 09
CI/CD SYSTEMS PIPELINE CONSTRUCTION

04 / Job & Credential Setup

Build the Jenkins pipeline structure and configure authenticated access to the GitHub repository. Never use raw GitHub passwords; always use a Personal Access Token (PAT) stored securely in Jenkins.

Step 1: Create Pipeline Job

Jenkins Dashboard -> New Item > Name: github-webhook-pipeline > Type: Pipeline Pipeline Definition: Pipeline script Initial Script: pipeline { agent any stages { stage('Test') { steps { echo 'Build OK' } } } }

Step 2: Configure Secure Credentials

Navigate to Pipeline Syntax -> checkout: Check out from version control. Generate the Groovy snippet using a new credential of type Username with password. Use your GitHub username as the username, and the PAT as the password.

GOTCHA

GitHub has deprecated password authentication for Git operations. Using your account password will result in a 403 Forbidden error during checkout. The PAT acts as a scoped, revocable proxy for your password.

INTERVIEW CHECK

Q: What is the difference between a PAT and a password?

A: A password grants full access to an account. A PAT is a scoped token that limits access to specific repositories and actions, can have an expiration date, and can be revoked without changing the account password.

CI/CD ENGINEERING MANUAL CH 01  |  05 / 09

CI/CD SYSTEMS CONTAINER DELIVERY

01 / The Container Lifecycle

Moving from source code to a running application requires a deterministic path. The code must be compiled, packaged with its dependencies, and shipped as an immutable artifact. In modern CI/CD, this artifact is a Docker image.

01 SOURCE Git checkout PASSED
02 BUILD docker build RUNNING
03 ARTIFACT Image tagged PUSHING
04 REGISTRY Docker Hub WAITING
05 DEPLOY FLOCI Env WAITING

WHAT

A pipeline that pulls source code, builds a Docker image, tags it with a unique build identifier, pushes it to a central registry, and optionally deploys it to a target environment.

WHY

Containerizing the application ensures environment parity. The exact artifact that passed CI is the one deployed, eliminating "it works on my machine" discrepancies.

WHEN

On every commit or merge to the main branch. The pipeline triggers automatically via webhook, executing the build and push sequence.

WHAT CHANGES

The release unit shifts from raw source code to a versioned, immutable container image. The registry becomes the source of truth for deployable software.

WHY THIS EXISTS

Without a standardized packaging format, deployment scripts must understand the application's dependency tree. A Docker image bundles the OS, libraries, and code into a single, static unit, radically simplifying the deployment target.

CI/CD SYSTEMS SECURE AUTHENTICATION

03 / Registry Authentication

To push an image to a private or public Docker Hub repository, Jenkins must authenticate. Credentials must be stored securely in Jenkins and injected at runtime, never hardcoded into the Jenkinsfile.

Credential Configuration

In Jenkins, navigate to Manage Jenkins → Credentials and add a "Username with password" credential. Use your Docker Hub username and an Access Token (not your account password).

PIPELINE SNIPPET

withCredentials([ usernamePassword( credentialsId: 'dockerhub-creds', usernameVariable: 'DOCKER_USER', passwordVariable: 'DOCKER_PASS' ) ]) { sh 'echo $DOCKER_PASS | docker login -u $DOCKER_USER --password-stdin' }

EXECUTION RESULT

[Pipeline] stage [Pipeline] withCredentials Masking supported pattern matches of $DOCKER_USER or $DOCKER_PASS [Pipeline] sh + echo **** Login Succeeded

GOTCHA

Docker Hub has deprecated password authentication for CLI push operations. You must generate a Personal Access Token (PAT) from Docker Hub's Account Settings → Security and use that token as the password in Jenkins.

INTERVIEW CHECK

Q: Why use --password-stdin instead of -p <password>?

A: Using -p on the command line exposes the password in the process list and shell history, which other users on the system could read. --password-stdin pipes the token securely via standard input, preventing it from being logged.

CI/CD SYSTEMS PIPELINE DEFINITION

04 / Jenkinsfile Construction

The declarative pipeline orchestrates the build, tag, and push sequence. Environment variables capture the image name and build tag, ensuring traceability between the Git commit, the Jenkins build number, and the Docker image.

pipeline { agent any environment { IMAGE_NAME = "myusername/app" IMAGE_TAG = "build-${env.BUILD_NUMBER}" } stages { stage('Code Checkout') { steps { checkout scm } } stage('Docker Build') { steps { sh "docker build -t ${IMAGE_NAME}:local ." } } stage('Image Tagging') { steps { sh "docker tag ${IMAGE_NAME}:local ${IMAGE_NAME}:${IMAGE_TAG}" } } stage('Image Push') { steps { sh "docker push ${IMAGE_NAME}:${IMAGE_TAG}" } } } }
Generated Artifact
myusername/app:build-123

WHY IT MATTERS

Tagging the image with build-${BUILD_NUMBER} creates an immutable, traceable link to the Jenkins execution. If a deployment fails, you can immediately pull the exact image that was deployed and inspect it. Using :latest destroys this traceability.

CI/CD ENGINEERING MANUAL CH 02  |  08 / 08
CI/CD SYSTEMS MULTIBRANCH PIPELINES

01 / Multibranch Foundations

A standard pipeline executes a single predefined script. A Multibranch Pipeline is structurally different: it is a folder of individual pipeline jobs, one per discovered branch. Jenkins scans the repository, finds branches, and looks for a Jenkinsfile to build with.

01 SCAN REPO Periodic or manual PASSED
02 DISCOVER Filter: main dev stg PASSED
03 JENKINSFILE Locate in branch root RUNNING
04 EXECUTE Create sub-job WAITING
05 ORPHAN Cleanup deleted SKIPPED

WHAT

A Jenkins job type that automatically creates a sub-job for every branch in a Git repository containing a Jenkinsfile.

WHY

It eliminates the need to manually create and configure a new Jenkins job every time a developer creates a new branch.

WHEN

On a periodic schedule (e.g., every 5 minutes) or manually triggered. This task deliberately ignores webhooks to simulate an air-gapped environment.

WHAT CHANGES

The relationship between source code and CI inverts. The repository defines the jobs, not Jenkins. Branch deletion leads to job orphaning.

WHY THIS EXISTS

In dynamic environments with feature branches, manually managing Jenkins jobs is impossible. Multibranch pipelines push job creation down into the repository itself, making the CI configuration version-controlled and branch-specific.

CI/CD SYSTEMS SHARED LIBRARIES

01 / Reusable Pipeline Logic

As pipeline complexity grows, duplicating Groovy logic across dozens of Jenkinsfiles creates a maintenance nightmare. A Shared Library allows you to store versioned Groovy classes in a standard Git repository and import them into any pipeline.

01 SOURCE Groovy repository PASSED
02 REGISTER Jenkins Config PASSED
03 IMPORT @Library('lib') _ RUNNING
04 INSTANTIATE new UatInput() WAITING
05 EXECUTE Conditional run WAITING

WHAT

A Git repository containing Groovy code that Jenkins dynamically downloads and makes available to pipelines via an import statement.

WHY

To enforce DRY (Don't Repeat Yourself) principles in CI/CD. Updates to shared logic propagate to all pipelines without modifying individual Jenkinsfiles.

WHEN

When multiple pipelines share common logic: deployment steps, approval gates, metric parsing, or custom build wrappers.

WHAT CHANGES

Pipelines become thinner. Complex business logic is abstracted into testable Groovy classes, moving Jenkins configuration closer to standard software engineering.

WHY THIS EXISTS

Without shared libraries, organizations end up with hundreds of bloated Jenkinsfiles that are impossible to update. A shared library transforms CI/CD logic into a versioned, testable software dependency.

01 / The Infrastructure Pipeline

Infrastructure as Code (IaC) requires the same rigorous CI/CD practices as application code. However, unlike application deployments, infrastructure changes can cause immediate, irreversible state shifts. The pipeline must therefore include strict validation and manual approval gates before applying changes.

02 INIT Provider download PASSED
03 PLAN State diff PASSED
04 APPROVE Human review WAITING

WHAT

A Jenkins pipeline that executes Terraform commands against a simulated AWS environment (FLOCI) to provision VPCs, subnets, and compute resources.

WHY

To practice infrastructure automation safely. FLOCI mimics the AWS API without incurring real costs, allowing teams to test CI/CD workflows aggressively.

WHEN

Triggered automatically by a GitHub webhook on push, but pauses for manual approval before the destructive apply stage.

WHAT CHANGES

Infrastructure moves from manual CLI execution to a versioned, peer-reviewed, automated pipeline. State shifts become deliberate, logged events.

WHY THIS EXISTS

Without a pipeline, infrastructure drifts. Engineers apply changes locally, state files diverge, and recovery becomes impossible. A pipeline enforces a single, auditable path from code to cloud.

Jenkins Input Step

stage('Approve') { steps { input message: 'Apply this Terraform plan?', ok: 'Approve' } }

GOTCHA

If the pipeline is aborted at the input step, Jenkins marks the build as ABORTED, not FAILED. Ensure your post actions distinguish between failure (requiring a mail alert) and abort (a deliberate human choice).

WHY IT MATTERS

Automation stops here because a human decision is required. The plan output is the contract; the apply is the execution. Skipping this gate removes accountability from the infrastructure lifecycle.

05 / FLOCI Provider Configuration

To target FLOCI instead of real AWS, the Provider.tf must override the default AWS endpoints. This intercepts the Terraform AWS provider's HTTP calls and routes them to the local simulation.

# Provider.tf provider "aws" { region = "us-east-1" # Redirect to FLOCI Simulation endpoints { ec2 = "http://floci-sim.local/ec2" s3 = "http://floci-sim.local/s3" elasticloadbalancing = "http://floci-sim.local/elb" } skip_credentials_validation = true skip_metadata_api_check = true skip_requesting_account_id = true }

COMMAND

$ terraform init

RESULT

Initializing the backend... Initializing provider plugins... Terraform has been successfully initialized!

WHY IT MATTERS

By skipping credential validation and overriding endpoints, Terraform operates in a sandbox. This allows engineers to test complex VPC topologies and EC2 deployments against a mock API, ensuring the IaC logic is sound before touching a real cloud billing account.

INTERVIEW CHECK

Q: Why use FLOCI instead of a real AWS Sandbox account?

A: Real AWS sandboxes still incur costs and carry the risk of accidental production impact if IAM boundaries are misconfigured. FLOCI provides a zero-cost, zero-risk API mock that is ideal for testing the CI/CD pipeline mechanics themselves.
